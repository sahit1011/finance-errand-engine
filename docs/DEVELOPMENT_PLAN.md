# Errand Agent: Development Plan

We build eight vertical slices, and each ends in something runnable with its own proof. Core work comes
first and needs no installs. Model work comes after the must-haves are solid, as the assignment asks.

Slices 1-7 are built. Slice 8 is in progress.

## Slices

| # | Slice | What gets built | Proof |
| --- | --- | --- | --- |
| 1 | Walking skeleton | `git init`, project setup, mock tools and ledger, scripted model, SQLite, trace file, one happy-path booking through the chat loop | `uv run pytest` passes scenario 1; `uv run errand demo happy_path` prints a booking and writes a trace |
| 2 | Approval and booking safety | Approval records, typed pending questions, stop, gateway check, idempotency, timeout recovery, crash and restart, undelivered replies | Scenarios 7, 9-17, 28, 29, 32, 33, 37, 38, 39 and 40 pass, including crash injection |
| 3 | All three actions | Reschedule, cancel, duplicate check, price lookup | Scenarios 18, 19, 27, 30 and 42 pass |
| 4 | Conversation and memory | Ask-only-what-is-missing, corrections, "same as last time", memory view, correct and forget | Scenarios 2, 3, 4, 8, 20-22, 34 and 41 pass across sessions |
| 5 | Hardening | Caps, untrusted content handling, trace sanitising, invariants on every run, generated eval table | Scenarios 5, 6, 23-26, 31, 35 and 36 pass, so all 42 pass offline; `eval_results.md` is generated; breaking a rule on purpose fails evals |
| 6 | Live chat | Install llama.cpp, add one local LLM behind the existing interface, wall-clock review | A real chat books through to verified success, with trace recorded |
| 7 | Model routing | Labelled turn set, router candidates, ladder, measured comparison | Results table from a real run, with quality, latency and memory |
| 8 | Deliverables | README, design note, chosen raw trace, final `BUGS.md`, demo recording | Fresh clone runs and tests in 3 commands or fewer; every box below is ticked |

Scenario numbers refer to the table in [SPECS.md](SPECS.md#evals).

## Working rules

- Keep `BUGS.md` from the first commit, so the 3 reported bugs are real and each has a regression test.
- Write failing tests first for approval and recovery rules.
- Run the checks before and after each slice, and report real output.
- Have a fresh subagent review each multi-file slice against these docs.
- Revise these docs explicitly if the build shows them to be wrong.

## Deliverables

- [ ] Git repo with implementation, mocks and tests; README runs and tests it in 3 commands or fewer
- [ ] Design note of at most 2 pages covering state model, approval enforcement, idempotency and
      recovery, memory and observability, ending with what breaks first at 100x and what we would change
- [ ] Eval table generated by the test run
- [ ] 3 real bugs: what broke, why, the fix, and the regression test
- [ ] One raw end-to-end trace with a timeout-after-success, plus an annotated excerpt in the design note
- [ ] Demo recording of 3-5 minutes: one full booking, one live failure, chat and trace side by side

## Technical risks

| Risk | What we know so far | How we find out |
| --- | --- | --- |
| Memory limit | The Mac has 16 GB; all three models ran together, with free memory down to 14%; the files total 8.7 GB | Measured in slice 7 |
| Model files | All three are downloaded and their checksums match | Done |
| Licences | Both Qwen3.5 LICENSE files are Apache 2.0; EmbeddingGemma 2's model card and Laya's README say Apache 2.0 | Done |
| Reviewer setup | The 3-command setup relies on `uv`, which reviewers may not have | README lists it as the one prerequisite |
| Laya accuracy | Not measured: running its package was blocked by a permission check on this machine | Allow it, then add it to the comparison |
| Python version | The default here is 3.14; 3.12 is available and will be pinned | First install in slice 1 |
