# Errand Agent: Product Requirements

The product lets one user book, reschedule and cancel home-service errands by chat. It must never
double-book, act without approval, or obey text inside a provider review.

Source of requirements: the Orange Invest "Founding AI Engineer: Errand Agent" assignment, which is not in
this repo.

## Decisions

| Decision | Choice | Why |
| --- | --- | --- |
| Core deliverable | Engine and chat first; models are a replaceable part | None of the 8 must-haves needs a live model to prove it |
| Runtime | Everything runs on the Mac, with no cloud LLM or API | Privacy; the assignment says an LLM API is optional |
| Language and storage | Python 3.12, SQLite, pytest | Little setup for reviewers; SQLite survives restarts |
| Live model server | llama.cpp (`llama-server`) | Binds to 127.0.0.1 by default and supports JSON schema output |
| Eval model | Scripted and recorded, never live | Required by must-have 8 |
| Nice-to-have | Model routing, built last | The spec allows at most one; this one matches our interest in decision models |
| Tool contract | Unchanged | The spec calls it fixed |
| Demo | Two terminal panes: chat and live trace | Meets the side-by-side requirement |
| Planning | No scope cuts for the 10-12 hour time box | Our choice; the 5-day submission window still applies |

## Problem

Booking a plumber takes several steps: comparing providers, holding a slot and handling failures. An
agent can do this, but an agent that spends money must stay trustworthy when the provider API fails,
the process crashes or a review contains hostile instructions.

## Users

- **End user:** a person arranging home services in India, with prices in ₹. They chat and approve
  actions.
- **Reviewer:** an Orange Invest engineer who runs the repo, reads the traces and checks the evals.

## Goals

1. Complete booking, reschedule and cancel conversations end to end through chat.
2. Enforce all 8 must-haves in code, each proven by an automated test.
3. Run entirely on the local machine, with tests needing no model or network.
4. Make every run explainable from its trace alone.

## Non-goals

- Real providers, payments or external services.
- Multi-user accounts, login or a web interface.
- Proactive follow-up, because the spec allows only one nice-to-have.

## User journeys

| Journey | Example request | What must happen |
| --- | --- | --- |
| New booking | "Find a plumber for my kitchen tap this week, mornings only, under ₹1,500." | Asks only for what is missing (area here), shows options within budget, holds the chosen slot, asks approval at the quoted price, books and verifies |
| Reschedule | "Move my AC servicing to Saturday." | Finds the booking (asks if several match), shows Saturday slots, asks approval, reschedules and verifies |
| Repeat provider | "Book the same electrician as last time, but not before 10 a.m." | Finds the provider in `list_bookings`, applies the 10 a.m. limit to this request only, then follows the booking flow |
| Cancel | "Cancel my plumber on Friday." | Finds the booking, asks approval, retries after the transient 503, verifies |
| Memory | "What do you remember about me?" | Shows each fact as stated or inferred, and lets the user correct or forget it |

## Requirements

| # | Must-have | Done means | Proved by |
| --- | --- | --- | --- |
| 1 | Workflow state | Known facts are never re-asked; a correction changes only that detail | Evals on missing details and corrections |
| 2 | Approval | No write without an approval record for the exact action, provider, slot and price; any change voids it | Evals on price or slot change and on a model faking approval |
| 3 | Booking correctness | No duplicates across repeated "yes", retries or restarts; success is reported only after verification | Mock ledger checks on timeout, repeat and restart evals |
| 4 | Untrusted output | Reviews cannot change intent, permissions or approval | Evals with hostile reviews and a hijacked scripted model |
| 5 | Bounded execution | Hard caps on model turns, tool calls and wall-clock time; every exit ends with a clear message | Limit and unknown-error evals |
| 6 | Memory | Facts persist across sessions; view, correct and forget work; inferred facts need confirmation; forgotten facts stay gone | Memory evals across sessions |
| 7 | Traces | One trace per run, with no secrets | Trace checks after every eval |
| 8 | Evals | 15 or more offline scripted scenarios, asserting outcomes and invariants | `pytest` run that generates the eval table |

## Success criteria

- The README gets the project running and tested in 3 commands or fewer, with no model installed.
- All evals pass offline, and the eval table is generated by the test run.
- Breaking a rule on purpose, such as removing the approval check, makes evals fail.
- All 6 deliverables are complete, including 3 real bugs and a timeout-after-success trace.
